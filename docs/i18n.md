# I18n Architecture

## Source of truth

The runtime source of truth for supported locales is `config/locales.php`.

Each locale defines:

- `code`
- `name`
- `native_name`
- `direction`
- `enabled`
- `fallback`
- `hreflang`
- `flag`

Laravel runtime helpers live in:

- `app/Support/Localization/LocaleConfig.php`
- `app/Support/Localization/TranslationCatalog.php`
- `app/Support/Localization/JsonFallbackTranslator.php`

`Language` database records are not the runtime source of truth. They can remain as administrative metadata or legacy data, but routes, middleware, HTML language attributes and JSON catalogs are governed by config.

## Translation layers

### JSON files

UI copy lives in:

- `lang/en.json`
- `lang/es.json`
- `lang/ar.json`

These files are the canonical translation catalogs for fixed product UI.

Stable key conventions:

- `common.*`
- `actions.*`
- `auth.*`
- `admin.*`
- `public.*`
- `catalog.*`
- `templates.*`
- `errors.*`
- `validation.*`
- `navigation.*`

### Legacy PHP language files

Legacy files still exist for backward compatibility:

- `lang/en/admin.php`
- `lang/es/admin.php`
- `lang/en/public.php`
- `lang/es/public.php`

They are intentionally preserved during migration because some structured arrays and pluralized strings still rely on them. The custom translator now gives priority to JSON exact keys, so JSON can become the canonical layer without deleting the older files prematurely.

### Database-translatable business content

Business content remains in database-backed translations:

- `template_translations`
- `invitation_category_translations`
- `templates.default_content`

Use DB translations for:

- template names
- localized slugs
- meta title and meta description
- category names and descriptions
- editable template content

Do not move editable business content into `lang/*.json`.

## Locale resolution flow

1. Requests enter localized routes with a `/{locale}` prefix.
2. `app/Http/Middleware/SetLocale.php` validates the locale and calls `app()->setLocale(...)`.
3. Blade layouts render `lang` and `dir` using `app/Support/Localization/LocaleConfig.php`.
4. Laravel translation calls can resolve exact JSON keys through `app/Support/Localization/JsonFallbackTranslator.php`.
5. React pages receive only the translation subset they need via `app/Support/Localization/PublicViewData.php`.
6. React uses `resources/js/lib/i18n.js` to access `t(key)`.

## React integration

Each public React page receives:

- `i18n.locale`
- `i18n.fallbackLocale`
- `i18n.direction`
- `i18n.messages`

`messages` is a per-page subset, not the whole dictionary.

Current bridge entry points:

- `resources/js/app.js`
- `app/Support/Localization/PublicViewData.php`

## RTL support

Locales declare `direction` in `config/locales.php`.

Blade layouts render:

```html
<html lang="ar" dir="rtl">
```

RTL-aware files include:

- `resources/views/layouts/public.blade.php`
- `resources/views/layouts/auth.blade.php`
- `resources/views/layouts/admin.blade.php`
- `resources/css/app.css`
- `resources/js/components/public/Header.jsx`

When adding an RTL language:

1. Set `direction` to `rtl` in config.
2. Create `lang/{locale}.json`.
3. Review dropdowns, drawers, overlays and text alignment in UI.

## Integrity checks

Run:

```bash
php artisan i18n:check
```

The command validates:

- configured locales without JSON files
- JSON files not declared in config
- missing keys compared to the base locale
- extra keys
- empty values

Implementation lives in `routes/console.php`.

## Adding a new language

1. Copy `lang/en.json` to `lang/fr.json`.
2. Translate values only. Keep every key unchanged.
3. Register `fr` in `config/locales.php` with its metadata.
4. Set `direction` to `ltr` or `rtl`.
5. Run `php artisan i18n:check`.
6. Review public pages, auth screens, admin navigation and template editor.
7. Add database content translations for categories, templates, slugs and template default content where needed.

## Recommended translation workflow with ChatGPT

You can send a locale file such as `lang/en.json` and ask:

> Translate only the values. Preserve exactly the same keys and JSON structure.

That workflow is now safe because the application depends on stable semantic keys instead of phrase-as-key catalogs.
